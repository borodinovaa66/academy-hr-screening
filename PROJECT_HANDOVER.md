# Передача проекта Academy HR Screening в разработку и сопровождение

Документ нужен для передачи проекта инженерам-разработчикам, DevOps/инженеру сопровождения и бизнес-владельцу со стороны HR. Он описывает, где находится код, как устроено приложение, какие доступы нужны, как деплоить, где смотреть логи, что нельзя потерять и какие зоны ответственности должны быть закреплены.

Важно: в этом документе намеренно нет паролей, токенов, приватных ключей и API-ключей. Их нужно передавать отдельно через менеджер паролей или другой защищенный канал.

## 1. Кратко о продукте

`Academy HR Screening` - внутреннее HR/SaaS-приложение для первичного отбора кандидатов.

Основной сценарий:

1. HR или руководитель открывает воронку по вакансии.
2. Кандидат получает ссылку на анкету.
3. Кандидат проходит опросник в формате чат-интерфейса.
4. Система считает баллы, стоп-факторы, рекомендации.
5. Сильным кандидатам выдается тестовое задание.
6. Кандидат прикрепляет ссылку на Google Документ с тестовым.
7. Руководитель и ИИ оценивают тестовое.
8. В админке формируется итоговая рекомендация по кандидату.
9. В перспективе воронка продолжается до интервью и календаря.

Текущий production URL:

```text
https://hr.academy-management.ru
```

Админка:

```text
https://hr.academy-management.ru/#admin
```

GitHub-репозиторий:

```text
https://github.com/borodinovaa66/academy-hr-screening
```

## 2. Текущий технический стек

- Backend: Node.js 22+, стандартный HTTP-сервер.
- База данных: SQLite через `node:sqlite`.
- Frontend: plain HTML/CSS/JS без React/Vue.
- Авторизация: HttpOnly cookie sessions, пользователи в SQLite.
- Reverse proxy: Nginx.
- HTTPS: Let's Encrypt / Certbot.
- Сервер: Ubuntu 24.04 LTS в Yandex Cloud.
- ИИ: YandexGPT, OpenAI оставлен как альтернативный провайдер.
- Почта: SMTP через Yandex 360, ящик `hr@academy-management.ru`.
- Telegram: бот для deep-link привязки кандидатов.
- HeadHunter: OAuth/API, webhook и синхронизация откликов.

В проекте нет npm-зависимостей. Запуск идет напрямую через Node:

```bash
npm start
```

## 5. Какие доступы нужно передать инженерам

### 5.1. GitHub

Нужно добавить инженеров в приватный репозиторий:

```text
https://github.com/borodinovaa66/academy-hr-screening
```

Минимально:

- разработчики: `Write`;
- технический лидер: `Maintain`;
- владелец продукта: `Read` или `Triage`;
- внешний подрядчик: лучше отдельный временный доступ с ограниченным сроком.

Правило: вся разработка должна идти через ветки и Pull Request, не напрямую в `main`.

Рекомендуемая схема:

```text
main                 production-ready код
develop              интеграционная ветка, если команда будет работать параллельно
feature/...          новая функциональность
fix/...              исправления
hotfix/...           срочные production-правки
```

### 5.2. SSH на сервер

Инженерам нужно выдать персональные SSH-ключи, не общий ключ.

Каждый инженер присылает публичный ключ вида:

```text
ssh-ed25519 AAAA... engineer-name
```

DevOps добавляет ключ в:

```text
/home/ubuntu/.ssh/authorized_keys
```

Доступ:

```bash
ssh ubuntu@93.77.178.9
```

После добавления доступ проверить:

```bash
ssh ubuntu@93.77.178.9 "hostname && whoami"
```

Важно: приватные ключи не пересылать в чатах и не хранить в репозитории.

### 5.3. Yandex Cloud

Нужно выдать доступ к облаку/каталогу, где создана VM.

Минимально инженеру сопровождения нужны права:

- смотреть VM;
- управлять сетью/security groups при необходимости;
- смотреть диски/snapshots;
- управлять сервисными аккаунтами только если он отвечает за ИИ/API.

Рекомендуемый подход: создать отдельную группу `hr-screening-engineers` и выдать права группе, а не каждому вручную.

- `YANDEX_GPT_API_KEY`;
- `OPENAI_API_KEY`;
- SQLite-база production;
- backup-файлы базы.

### Текущая временная схема передачи через production-сервер

На момент передачи выбран практичный временный вариант: рабочие production-секреты остаются на сервере, а разработчики с SSH-доступом смотрят их на сервере самостоятельно.

Фактические пути:

```text
/etc/hr-screening/app.env
/etc/academy-ai-relay/app.env
```

Фактические директории сервисов:

```text
/opt/hr-screening
/opt/academy-ai-relay
```

Как разработчику посмотреть переменные:

```bash
ssh ubuntu@93.77.178.9
sudo cat /etc/hr-screening/app.env
sudo cat /etc/academy-ai-relay/app.env
```

Что важно:

- значения из этих файлов нельзя копировать в GitHub, Bitrix24, Telegram, обычную почту и документы;
- для локальной разработки лучше использовать отдельные тестовые ключи;
- если production-ключ все же временно нужен локально, копировать только нужные переменные в локальный `.env`, который игнорируется Git;
- после завершения передачи нужно заменить все секреты, которые ранее пересылались в чатах;
- доступ к серверу фактически дает доступ к production-секретам, поэтому SSH должен быть персональным и отзываться при уходе человека из проекта.

### Целевая правильная схема

После стабилизации проекта секреты лучше перенести в корпоративное хранилище:

1. Создать общий корпоративный password vault: 1Password, Bitwarden, Keeper, Yandex Lockbox или аналог.
2. Создать отдельную папку `Academy HR Screening`.
3. Разложить секреты по записям:
   - `Production server SSH`;
   - `Production app env`;
   - `Yandex Cloud`;
   - `Yandex 360 SMTP`;
   - `HeadHunter API`;
   - `Telegram bot`;
   - `AI providers`;
   - `NIC.ru DNS`.
4. Выдать доступ только тем, кому он нужен.
5. После передачи заменить все секреты, которые ранее отправлялись в чатах.

Проверка:

Проверить в браузере:

```text
https://hr.academy-management.ru
```

## 9. Rollback

Если после деплоя приложение сломалось:

1. Проверить логи:

```bash
sudo journalctl -u hr-screening -n 200 --no-pager
```

2. Остановить сервис:

```bash
sudo systemctl stop hr-screening
```

3. Вернуть предыдущую папку приложения:

```bash
sudo rm -rf /opt/hr-screening
sudo cp -a /opt/hr-screening.backup.YYYYMMDDHHMMSS /opt/hr-screening
sudo chown -R hrapp:hrapp /opt/hr-screening
```

4. Запустить:

```bash
sudo systemctl start hr-screening
sudo systemctl status hr-screening --no-pager
```

Если проблема в базе, восстановление делать только из свежего backup и только после копии текущей базы.

Что обязательно проверить при приемке:

```bash
systemctl list-timers | grep hr-screening-backup
ls -lah /var/backups/hr-screening
```

Нужно не просто видеть backup-файлы, а хотя бы раз протестировать восстановление на копии.

Контрольный restore-тест:

1. Скопировать backup на staging или локально.
2. Запустить приложение на копии базы.
3. Проверить, что открываются:
   - админка;
   - список кандидатов;
   - карточка кандидата;
   - тестовое задание;
   - журнал коммуникаций.

## 11. Основные API и функции

Кандидатская часть:

- `GET /v/:vacancyCode` - анкета конкретной вакансии;
- `POST /api/submissions` - отправка анкеты;
- `POST /api/submissions/:id/test-assignment` - прикрепление тестового;
- `POST /api/submissions/:id/test-assignment/viewed` - фиксация открытия тестового;
- `POST /api/events` - события воронки.

Админка:

- `POST /api/auth/login`;
- `POST /api/auth/logout`;
- `GET /api/admin/submissions`;
- `GET /api/admin/submissions/:id`;
- `DELETE /api/admin/submissions/:id`;
- `GET /api/admin/analytics`;
- `POST /api/admin/ai-insights`;
- `GET /api/admin/config`;
- `PUT /api/admin/config`;
- `GET /api/admin/users`;
- `POST /api/admin/users`;
- `PUT /api/admin/users/:id`.

HeadHunter:

- `GET /api/admin/hh/status`;
- `GET /api/admin/hh/oauth-url`;
- `GET /api/hh/oauth/callback`;
- `POST /api/admin/hh/webhook/setup`;
- `POST /api/hh/webhook`;
- `POST /api/admin/hh/publications/:id/sync-responses`;
- `POST /api/admin/hh/responses/:id/send-questionnaire`.

Telegram:

- `POST /api/telegram/webhook`;
- deep-link используется для привязки кандидата к Telegram-чату.

## 13. Данные и персональные данные

Приложение хранит:

- имя и фамилию кандидата;
- email;
- телефон;
- ответы анкеты;
- ссылку/файл резюме;
- ссылку на тестовое;
- баллы;
- рекомендации;
- стоп-факторы;
- согласия;
- IP/user-agent при согласии;
- коммуникации;
- Telegram-привязку, если кандидат подключил бота.

Это персональные данные. Production-базу нельзя:

- отправлять в открытые чаты;
- загружать в публичные облака;
- прикладывать к GitHub issues;
- использовать на локальной машине без необходимости.

Для разработки лучше сделать обезличенный seed-дамп.

4. Изменение тестируется локально.
5. Создается Pull Request.
6. Второй разработчик смотрит review.
7. После approve изменение деплоится на staging.
8. После проверки идет production deploy.
9. В `CHANGELOG.md` фиксируется изменение.

Для ошибок:

```text
Bug report должен содержать:
- где увидели проблему;
- ссылка/экран;
- что ожидали;
- что произошло;
- скриншот;
- время ошибки;
- кандидат/вакансия, если применимо.
```

## 18. Что нужно сделать в ближайшую очередь

## 19. Известные ограничения текущей версии

- Это MVP, а не зрелая enterprise-система.
- SQLite подходит для пилота, но при росте нагрузки лучше перейти на PostgreSQL.
- Frontend большой и монолитный, его нужно постепенно дробить.
- Методология частично хранится в JSON-конфигурации, редактирование пока не идеальное для нетехнического HR.
- HH-интеграция зависит от прав аккаунта работодателя и возможностей API.
- Просмотры HH могут быть недоступны через API, тогда показываются только отклики и внутренняя аналитика.
- Email работает через SMTP, но для массовых отправок лучше транзакционный сервис.
- Для production нужны мониторинг и alerts.

## 20. Что нельзя делать после передачи

- Нельзя редактировать production-код прямо на сервере без фиксации в Git.
- Нельзя хранить production `.env` в репозитории.
- Нельзя использовать один общий SSH-ключ для всех.
- Нельзя копировать production-базу разработчикам без обезличивания.
- Нельзя менять DNS без записи в журнале изменений.
- Нельзя запускать массовую рассылку кандидатам без проверки шаблонов.
- Нельзя полностью отдавать финальное HR-решение ИИ.
