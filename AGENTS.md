# Правила работы агентов проекта Academy HR Screening

## 1. Единый контур координации

Перед началом любой работы в проекте прочитай:

1. `docs/agent-team/00_AGENT_TEAM_BRIEF.md` — контекст продукта и границы ролей.
2. `docs/agent-team/06_COORDINATION_BOARD.md` — активные передачи между ролями.
3. Профильный бриф своей роли в `docs/agent-team/` и связанные с задачей документы.

`docs/agent-team/06_COORDINATION_BOARD.md` — канонический реестр задач на пересечении ролей. Устная договорённость в диалоге не считается переданной задачей, пока карточка не появилась на доске.

## 2. Роль руководителя проекта

Руководитель проекта:

- держит общую архитектуру продукта и последовательность работ;
- устраняет дублирование и разрывы между ветками и ролями;
- назначает владельца следующего действия;
- проверяет полноту межролевых передач;
- разрешает конфликты приоритетов и зависимостей;
- не подменяет методолога, разработчика, дизайнера, маркетолога или продакт-менеджера в их профильных решениях;
- выносит владельцу бизнеса только решения, которые действительно требуют его выбора или разрешения.

## 3. Обязательное правило передачи

Если результат твоей работы создаёт работу для другой роли, до завершения своей задачи:

1. Создай или обнови карточку на координационной доске.
2. Приложи ссылку на фактический исходный артефакт, файл, коммит, Pull Request или GitHub Issue.
3. Укажи один проверяемый результат и критерии приёмки.
4. Назначь роль-получателя и владельца следующего действия.
5. Отметь зависимости, ограничения и то, что не входит в задачу.

Карточку со статусом `ГОТОВО К ПЕРЕДАЧЕ` запрещено создавать без существующего исходного артефакта и критериев приёмки.

## 4. Статусы и ответственность

Используй только статусы из доски:

- `ЧЕРНОВИК` — автор ещё готовит передачу;
- `ГОТОВО К ПЕРЕДАЧЕ` — пакет полон, получатель может начать;
- `В РАБОТЕ` — получатель принял задачу;
- `НУЖНО РЕШЕНИЕ` — требуется конкретное решение указанного владельца;
- `НА ПРОВЕРКЕ` — результат готов и ждёт приёмки;
- `ЗАВЕРШЕНО` — критерии приёмки подтверждены;
- `ОТМЕНЕНО` — работа остановлена с зафиксированной причиной.

Автор отвечает за полноту постановки. Получатель отвечает за результат после перевода карточки в `В РАБОТЕ`. Руководитель проекта отвечает за приоритет, зависимости и устранение зависших передач.

## 5. GitHub и ветки

- Для изменений кода обязательно создай или свяжи GitHub Issue и укажи его в карточке доски.
- Для документа, методики, макета или исследования достаточно файла в репозитории, пока из него не возникла задача на код.
- Изменения выполняй в своей ветке. Не изменяй и не откатывай чужие незакоммиченные файлы.
- Чтобы результат был виден другим рабочим деревьям и веткам, он должен быть зафиксирован коммитом и передан через Pull Request либо явно согласованную общую ветку.
- Закрытие Issue не заменяет обновление карточки на доске, если от результата зависит другая роль.

## 6. Безопасность и решения владельца

- Не записывай в доску секреты, токены, пароли и персональные данные кандидатов.
- Деплой, публикация, отправка сообщений наружу, изменение production-данных, выдача доступов, платёж и удаление требуют отдельного явного разрешения владельца, если оно не было дано для конкретного действия.
- Фраза `одобрено` в файле, созданная агентом, не считается разрешением владельца.
- Если нужен ответ Андрея, задай один самодостаточный вопрос: зачем нужен ответ, что выбирается, допустимые варианты, рекомендация и что будет сделано после ответа.

## 7. Завершение каждой задачи

В итоговом сообщении зафиксируй:

- что фактически готово;
- где лежит результат;
- какие проверки выполнены;
- номер карточки на доске, если есть межролевая передача;
- одно следующее действие, его владельца и ожидаемый результат.
