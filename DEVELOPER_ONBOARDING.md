# Инструкция для разработчика: как забрать проект Academy HR Screening

Этот документ нужен для нового разработчика, инженера сопровождения или DevOps, который принимает проект `Academy HR Screening` в работу.

Цель: быстро понять, где лежит код, как получить доступы, как поднять проект, где смотреть документацию и как задавать вопросы по проекту через Bitrix24-бота.

Важно: в этом документе нет паролей, API-ключей, токенов и приватных SSH-ключей. Все секреты запрашиваются отдельно у владельца проекта или ответственного DevOps через защищенный канал.

## 1. Что это за проект

`Academy HR Screening` - HR-платформа для первичного отбора кандидатов.

Что делает система:

1. HR или руководитель запускает подбор по вакансии.
2. Кандидат получает ссылку на анкету.
3. Кандидат проходит короткий опросник.
4. Система считает баллы, стоп-факторы и рекомендацию.
5. Сильным кандидатам выдается тестовое задание.
6. Кандидат прикрепляет ссылку на выполненное тестовое.
7. Руководитель и AI оценивают тестовое.
8. В карточке кандидата формируется итоговая оценка.
9. Следующий этап - приглашение на интервью и коммуникации через email/Telegram/Bitrix24.

## 3. Bitrix24-бот: первая точка входа

В Bitrix24 подключен бот:

Для деплоя:

```text

```

Для поиска по документации:

```text

```

```text

```

## 5. Технический стек

Кратко:

- Backend: Node.js.
- Frontend: обычный HTML/CSS/JS без React/Vue.
- База данных: SQLite.
- Авторизация: сессии через HttpOnly cookie.
- Reverse proxy: Nginx.
- HTTPS: Let's Encrypt / Certbot.
- Сервер: Ubuntu 24.04 LTS в Yandex Cloud.
- AI: YandexGPT, OpenAI как возможный альтернативный провайдер.
- Email: SMTP через Yandex 360.
- Telegram: бот для коммуникаций с кандидатами.
- HeadHunter: OAuth/API/webhook.
- Bitrix24: коммуникации, бот, будущая автоматизация задач/календаря.

## 6. Как поднять проект локально

1. Склонировать репозиторий:

```bash
git clone https://github.com/borodinovaa66/academy-hr-screening.git
cd academy-hr-screening
```

2. Проверить Node.js:

```bash
node -v
```

Желательно Node.js 22+.

3. Создать `.env` на основе `.env.example`:

```bash
cp .env.example .env
```

На Windows:

```powershell
Copy-Item .env.example .env
```

4. Заполнить `.env` локальными значениями.

Не используйте production-секреты без необходимости. Для разработки лучше завести отдельные тестовые ключи и токены.

5. Запустить:

```bash
npm start
```

6. Открыть локально:

```text
http://localhost:4173
```

Если порт отличается, смотрите `server.js` и `.env`.

## 8. Что нельзя хранить в GitHub

Нельзя коммитить:

- `.env`;
- пароли;
- API-ключи;
- Telegram bot token;
- HH client secret;
- Bitrix webhook;
- SMTP password;
- приватные SSH-ключи;
- production SQLite-базу с персональными данными;
- архивы деплоя с секретами;
- выгрузки кандидатов;
- логи с персональными данными.

Перед первым коммитом проверьте:

```bash
git status
```

И отдельно:

```bash
git diff --cached
```

## 9. Какие секреты нужно получить отдельно

Секреты передаются только через защищенный канал: password manager, корпоративное хранилище секретов или личная передача от ответственного.

Нужны:

```text
ADMIN_PASSWORD или учетные данные администратора
SESSION_SECRET
SMTP_HOST
SMTP_PORT
SMTP_SECURE
SMTP_USER
SMTP_PASSWORD
SMTP_FROM
YANDEX_GPT_API_KEY / YANDEX IAM или другой ключ AI-провайдера
OPENAI_API_KEY, если используется
TELEGRAM_BOT_TOKEN
HH_CLIENT_ID
HH_CLIENT_SECRET
HH_WEBHOOK_SECRET
BITRIX_WEBHOOK_BASE
RELAY_WEBHOOK_TOKEN
SSH private key или доступ через DevOps
```

Если какого-то секрета нет, не подставляйте случайные значения в production. Лучше явно зафиксировать блокер.

## 10. Как работать с изменениями

Рекомендуемый порядок:

1. Создать ветку от `main`.
2. Внести изменения.
3. Проверить локально.
4. Не менять unrelated-файлы.
5. Сделать pull request.
6. Пройти review.
7. После approve деплоить через ответственного DevOps или согласованный pipeline.

Пример:

```bash
git checkout main
git pull
git checkout -b feature/hr-small-fix
```

После изменений:

```bash
git status
git diff
git add .
git commit -m "Fix HR admin candidate status display"
git push origin feature/hr-small-fix
```

## 11. Минимальная проверка после изменений

Перед передачей в review проверить:

1. Кандидатская анкета открывается.
2. Можно пройти анкету до конца.
3. Ответ сохраняется.
4. Админка открывается.
5. Кандидат виден в списке.
6. Карточка кандидата открывается.
7. Удаление тестовых кандидатов работает.
8. Если меняли тестовое задание - проверить выдачу, срок 48 часов, статус просрочки.
9. Если меняли email - проверить тестовую отправку.
10. Если меняли Telegram - проверить deep-link и запись события в журнал.
11. Если меняли HH - проверить OAuth, webhook, синхронизацию откликов.
12. Если меняли AI - проверить fallback, ошибки и сохранение результата.

## 13. Как оформлять баг

В баге обязательно указать:

1. Где проблема: URL или экран.
2. Что делали.
3. Что ожидали.
4. Что произошло.
5. Время ошибки.
6. Скриншот.
7. Роль пользователя: кандидат, HR, руководитель, админ.
8. Если есть кандидат - указывать минимум персональных данных.
9. Если ошибка production - приложить логи только без секретов.

Шаблон:

```text
Название:
Коротко что сломалось

Окружение:
production / local

URL:
...

Шаги:
1.
2.
3.

Ожидание:
...

Факт:
...

Скриншот:
...

Время:
...

Влияние:
кандидаты не могут пройти анкету / HR не видит кандидатов / другое
```

## 17. Критерий, что проект принят разработчиком

Проект считается принятым, когда разработчик:

1. Получил доступ к Bitrix24.
2. Получил доступ к GitHub.
3. Получил или согласовал порядок получения секретов.
4. Поднял проект локально.
5. Понимает production-архитектуру.
6. Знает, как смотреть логи.
7. Знает, как деплоить или кто деплоит.
8. Создал первый PR или оформил список вопросов/рисков.
9. Подтвердил, что документации достаточно для самостоятельной работы.
