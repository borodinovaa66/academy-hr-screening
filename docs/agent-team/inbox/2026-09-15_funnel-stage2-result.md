# Этап 2: версии и человеческое утверждение материалов

Дата: 2026-09-15. Карточка: HR-XFER-20260915-02. [Issue #2](https://github.com/borodinovaa66/academy-hr-screening/issues/2).

Статус: на проверке руководителя проекта. Основа: принятый этап 1, коммит `0ef0ef6`, ветка `codex/funnel-stage1` / PR #3. Изменения выполнены отдельно в `D:\Codex\HR-stage2`, ветка `codex/funnel-stage2`.

## Что реализовано

- Отдельный `src/funnelArtifacts.js`: текущая версия, новая неизменяемая версия содержимого, передача на проверку, утверждение и возврат.
- Сохранение создаёт черновик. Передача на проверку разрешена из `draft`/`rejected`; утверждение только из `review`; возврат из `review`/`approved` требует непустую причину.
- Каждое утверждение относится к текущей версии и фиксирует пользователя, имя входа, роль, время, номер версии, комментарий и результаты проверки критериев. Новая версия не наследует утверждение.
- Номер версии самой воронки изменяется при каждой операции. Устаревшая версия воронки или материала даёт 409, а повтор успешного запроса с тем же ключом возвращает сохранённый ответ без новых записей.
- Изменение/возврат профиля снимает согласования текущих зависимых материалов. Изменение профиля через старый адаптер делает то же самое с системной подписью в журнале.
- Материал, кроме профиля, можно утвердить только с привязкой к текущей утверждённой версии профиля. Импортированный материал без такой привязки нужно сначала сохранить новой версией.
- Закрытые и архивные воронки доступны только для чтения через новые методы.

## Решение по одному утверждению

Руководитель проекта явно подтвердил: одно утверждение одним уполномоченным человеком для каждого материала, включая тестовое. Исправлены Т-12, пояснение принимающего и строка итоговой матрицы в `SIX_FUNNEL_ARTIFACT_ACCEPTANCE_CRITERIA_V1.md`. Раздел 12 основного ТЗ не изменён.

Когда тестовое утверждает не пользователь с ролью `hiring_manager`, в Т-12 обязательно указываются имя ЛПР и дата подтверждения профессиональной уместности. Вторая подпись API не нужна. Это запись человеческого подтверждения, а не автоматическая проверка правдивости указанного факта.

## Права и безопасность

- Действующий владелец: все действия.
- HR: редактирование и передача всех материалов; по умолчанию утверждение текста вакансии, анкеты, тестового, первичного интервью; возврат всех материалов.
- Руководитель: старое право на вакансию плюс ограничение конкретным заказчиком из этапа 1; редактирование/передача профиля, текста вакансии, финального интервью; утверждение этих материалов и тестового; остальные материалы может читать и возвращать с комментарием.
- Допустимые роли утверждения настраиваются записью `configs.key=funnel_approval_policy`. Формат: объект с шестью типами материалов; каждое значение содержит одну группу ролей, например `"questionnaire": [["owner", "hr"]]`. В MVP требуется ровно одна группа. Настройка серверная, интерфейс управления ею не добавлялся. Неизвестная/служебная роль или повреждённая политика блокирует утверждение; владелец сохраняет полномочия при корректной политике.
- Идентичность определяется по актуальной записи `users`, а не по полям запроса и не по старой функции, превращающей неизвестные роли в HR. ИИ, системные роли и аккаунты с префиксом `system:`/`ai:` блокируются. Попытка передать `actorType`, `role`, `approvedByUserId`, `source` и подобные поля даёт 403.
- Предъявление действительной человеческой сессии является техническим основанием действия. API не может доказать физическое присутствие человека у компьютера; чужие сессии нельзя передавать автоматизации.
- Добавлена защита новых операций от межсайтовых запросов: токен связан с сессией, проверяется сервером; старые API не менялись. После перезапуска процесса нужно получить свежий токен.

## API

1. `GET /api/admin/funnels/csrf` возвращает `csrfToken` для текущей сессии.
2. `GET /api/admin/funnels/:id/artifacts/:type` возвращает материал, `funnelVersion`, версию профиля, текущий цикл проверки, перечень критериев, матрицу принимающих и подписи текущего цикла. У старой отозванной подписи `valid=false`.
3. `PUT /api/admin/funnels/:id/artifacts/:type` сохраняет новую версию.
4. `POST /api/admin/funnels/:id/artifacts/:type/submit` передаёт на проверку.
5. `POST /api/admin/funnels/:id/artifacts/:type/approve` утверждает.
6. `POST /api/admin/funnels/:id/artifacts/:type/reject` возвращает.

Все записи требуют заголовки `X-CSRF-Token` и `Idempotency-Key` (8–128 символов: латинские буквы, цифры, `. _ : -`). Тело обязательно содержит целочисленные `funnelVersion` и `artifactVersion`; для отсутствующего материала `artifactVersion=0`. После ответа нужно использовать новые версии. При смене данных создаётся новый ключ операции.

Пример сохранения (номера берутся из текущего GET):

```json
{"funnelVersion": 8, "artifactVersion": 1, "content": "Новый текст материала", "profileVersion": 1, "comment": "Уточнены условия"}
```

`content`: непустая строка, объект или массив, максимум 500 000 байт сериализованного содержимого. `profileVersion` для профиля не требуется; для остальных по умолчанию берётся текущая версия профиля, а переданный номер проверяется. Комментарий до 8000 символов.

Для утверждения передаются `criteriaVersion="six-materials-v1-2026-09-15"`, непустой `comment` и `checks`: ровно все критерии данного типа без пропусков и дублей. Пример одного элемента: `{"id":"А-01","result":"passed"}`. Разрешён `not_applicable` с обязательным `reason`. Непройденный критерий блокирует утверждение. Для Т-12 при утверждении не ЛПР: `{"id":"Т-12","result":"passed","lprConfirmation":{"name":"Имя руководителя","confirmedAt":"2026-09-15T10:00:00Z"}}`.

Ошибки: 401 без входа; 403 неверный токен/роль/подмена автора; 404 неизвестный тип или недоступная воронка; 400 некорректные данные/пропуски; 409 конфликт версий/ключей, запрещённый переход, непрошедшие критерии, неутверждённый профиль. Список и карточка этапа 1 сохранены. Новые ответы не кешируются.

## Хранение и аудит

Миграция добавляет `profile_version`, `review_cycle`, таблицы `funnel_artifact_approvals` и `funnel_artifact_operations`. Повтор миграции не удаляет подписи. Предыдущие версии содержимого сохраняются; переходы и отзыв утверждения прослеживаются в журнале. Все успешные операции атомарны вместе с записью журнала и ключа повтора. Сбой аудита откатывает всю операцию. Отвергнутые запросы изменений и повторы не создают успешных событий в журнале.

Адаптер не перезаписывает материалы, переведённые на источник `human`. Новые материалы не записываются обратно в старый опросник или публичные страницы: подключение потребителей относится к следующим этапам.
