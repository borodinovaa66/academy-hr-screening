2. после стабилизации собрать управляемый следующий релиз из проверенных веток.

Их нельзя объединять в один деплой. Перезаписывать сервер кодом из GitHub до снимка диска и выгрузки данных запрещено.

## Подтверждённая причина текущей недоступности

Сервер расположен в зоне `ru-central1-a`. На официальной странице состояния Yandex Cloud опубликован продолжающийся инфраструктурный инцидент: зоны `ru-central1-a` и `ru-central1-b` недоступны, Compute работает в других зонах.

Это объясняет одновременно:

- тайм-ауты 22, 80 и 443;
- недоступность SSH и рабочего домена;
- состояние VM `RUNNING` при фактической сетевой недоступности;
- ответ Compute API `Unavailable` при попытке создать снимок.

Текущая авария не вызвана сменой домена или выбором Git-ветки. При этом отсутствие копии данных вне зоны `ru-central1-a` остаётся нашим эксплуатационным пробелом.

## Что является нормой, а что проблемой

Нормально: код хранится в GitHub, а база, резюме и секреты не коммитятся.

Проблема: у production-данных нет проверенной внешней резервной копии, автоматических снимков и документированного восстановления. Доступ разработчика к GitHub поэтому не даёт ему данных для миграции.

## Безопасный порядок восстановления

### Шаг 1. Дождаться доступности диска или инструкции поддержки

Не выполнять restart, stop, delete или redeploy, пока Compute API не позволит создать снимок либо поддержка Yandex Cloud не даст другой подтверждённый способ сохранить диск.

Как только зона/диск доступны, создать аварийный снимок загрузочного диска с именем вида `hr-production-emergency-2026-10-14`. Снимок будет crash-consistent: это не заменяет нормальную SQLite-копию, но даёт точку отката до перезагрузки.

### Шаг 2. Перезапустить виртуальную машину после снимка

После готовности снимка выполнить обычный restart, не пересоздание и не удаление. Проверить 22/80/443, SSH, `nginx` и `hr-screening`.

### Шаг 3. Сначала выгрузить данные, затем чинить приложение

После возврата SSH:

1. остановить `hr-screening`, чтобы прекратить записи;
2. сохранить `/opt/hr-screening/data` целиком, включая SQLite, WAL/SHM и `uploads`;
3. создать SHA-256 архива;
4. хранить архив только в шифрованном хранилище с ограниченным доступом;
5. запустить сервис и проверить восстановление SQLite;
6. отдельно снять согласованную SQLite-копию штатным механизмом `.backup` или после чистого закрытия процесса.

Архив с персональными данными нельзя отправлять в чат, GitHub или обычной почтой.

### Шаг 4. Диагностировать первопричину

Проверить:

- `journalctl` для загрузки, nginx и `hr-screening`;
- свободное место, inode, память и OOM;
- локальные firewall/iptables;
- состояние сертификата;
- целостность SQLite (`PRAGMA integrity_check`, `PRAGMA foreign_key_check`);
- фактические хэши production-файлов и `version.json`.

### Шаг 5. Ввести постоянные страховки

- ежедневный снимок диска с ограниченным сроком хранения;
- отдельная ежедневная SQLite-копия и архив загрузок;
- ежемесячная проверка восстановления на изолированной машине;
- мониторинг HTTPS и заполнения диска;
- Yandex Lockbox и персональные IAM/SSH-доступы вместо общего ключа.

## Как передавать доступ разработчикам

Не нужен общий пароль от облака и не нужно передавать пароль работодателя HeadHunter.

Рекомендуемая схема:

- одному назначенному специалисту по миграции — персональный доступ к серверу и зашифрованному полному архиву;
- остальным разработчикам — обезличенная копия базы без резюме и персональных полей;
- секреты приложения — через Yandex Lockbox с ролью `lockbox.payloadViewer`;
- доступ в Yandex Cloud — через персональный IAM, который можно отозвать.

## HeadHunter

При смене домена нужны два разных действия:

1. владелец приложения в `dev.hh.ru` меняет разрешённый OAuth callback;
2. менеджер работодателя заново проходит OAuth, после чего сервер создаёт или обновляет webhook-подписку на новый URL.

В production-конфигурации должны совпадать `APP_PUBLIC_URL`, `HH_REDIRECT_URI` и `HH_WEBHOOK_URL`. Новый webhook проверяется тестовым событием и ответом 2xx. Старый домен нельзя отключать до проверки нового callback и webhook.

Пароль аккаунта работодателя разработчику не передаётся: владелец аккаунта авторизуется сам в браузере. Токены хранятся только в production-секретах.

## Какую версию кода использовать

Для аварийного восстановления: не выкладывать новый код. Нужно поднять текущий диск и проверить фактические хэши.

Для сверки последней известной production v79: коммит `64c1022`. Это лучший известный ориентир, но не доказательство побайтового совпадения с недоступным сервером.

Для следующего релиза:

- не использовать `origin/main` как production-базу: он заканчивается 2026-07-22;
- `codex/funnel-stage1`, `stage2`, `stage3` — последовательная цепочка, а не альтернативные версии; `stage3` содержит предыдущие этапы;
- этапы 1–3 проверены, но не закрывают HeadHunter-first, карантин и все старые маршруты кандидатов;
- `codex/funnel-stage4` не имеет законченного коммита/PR и не является релизом;
- `codex/manager-first-vacancy` / PR #7 добавляет первый вход руководителя, но не полную сборку шести материалов;
- техническая проба `merge-tree` показывает, что stage3 и manager-first могут быть объединены без Git-конфликта, но это ещё не функциональная приёмка.

Рекомендуемая база следующего релиза: новая интеграционная ветка от `codex/funnel-stage3` плюс PR #7, затем завершённые этапы HeadHunter-first/карантина и интерфейса. Только после теста миграции на копии production-базы эта ветка может стать кандидатом в релиз.

## Критерии завершения инцидента

- существует аварийный снимок диска;
- существует проверенный зашифрованный архив `/opt/hr-screening/data` и его SHA-256;
- SQLite проходит проверки целостности;
- домен, админка и публичная анкета отвечают;
- зафиксированы хэши и версия фактически работающего кода;
- настроены автоматические резервные копии и мониторинг;
- определён один владелец production-доступа и один владелец следующего релиза.

## Решение владельца

Владелец разрешил восстановить прежний домен и нормальную работу системы. В рамках этого разрешения допустимы два последовательных действия, когда Compute API снова станет доступен:

1. создать аварийный снимок загрузочного диска Yandex Cloud;
2. только после готовности снимка перезапустить `my-cloud-server` для возврата SSH и выгрузки данных.

Разрешение не включает деплой, изменение production-данных, HeadHunter, выдачу доступов разработчикам или удаление ресурсов. Текущий внешний блокер — недоступность Compute в `ru-central1-a`; до снятия блокера restart не выполняется.
