## Модель данных

К `vacancy_openings` добавлены `source`, `manual_status`, `opened_at`, `closed_at`, `last_status_sync_at`, `version`. Старый `status` сохранён только для совместимости. Новый статус вычисляется, а не записывается в дополнительное поле.

Созданы `funnel_artifacts`, `funnel_channels`, связующая таблица `funnel_legacy_publications`, индексы последних версий и уникальности внешнего номера HeadHunter. Добавлено поле роли утвердившего `approved_by_role`. К `submissions` и `hh_responses` добавлены nullable-ссылки `funnel_id`; существующие записи не перепривязаны по предположению.

Материалы из старой конфигурации переносятся как черновики. Флаг `publicFunnelApproved` не является утверждением. Изменение старого содержимого создаёт новую черновую версию, история сохраняется. Материал, редактируемый новым механизмом с источником не `legacy_*`, адаптер не перезаписывает.

Старое единственное `interview` относится к первичному интервью. Оно не дублируется в финальное. Отдельный финальный сценарий из файлов не импортируется без явной связи с конкретным запуском. Наличие документов вне базы не скрывает этот пробел.

Шаблон роли сам по себе не создаёт запуск. Публикации связываются только по существующим явным ссылкам. Неоднозначные и неподвязанные записи сохраняются: общий счётчик доступен владельцу и HR, предупреждение о конфликте есть в карточке. Ручное разрешение конфликтов и создание отсутствующих запусков относятся к следующей миграции/импорту.

Канал HeadHunter считается активным только по сохранённому снимку `hhMetrics` с датой получения и признаком `archived=false`. Простое `status=published` не подтверждает активность. Новых запросов к HeadHunter нет; дата снимка возвращается в ответе. Витрина не включается автоматически. Даты открытия/закрытия не выдумываются и могут оставаться пустыми.

## Договорённость API

- `GET /api/admin/funnels` возвращает `{ funnels, migration }`. Каждая строка содержит вычисленные `status`, `readiness` (счётчики и шесть состояний без содержимого), каналы, ответственных, версию, даты и предупреждения.
- `GET /api/admin/funnels/:id` возвращает `{ funnel }`: те же данные, шесть текущих материалов и до 200 последних событий истории данного запуска.
- Без сессии: 401. Неизвестная или недоступная карточка: одинаковый 404. Ответы с данными не кешируются.
- Владелец и HR читают все запуски. Руководитель должен иметь старое право на код вакансии; явно назначенный заказчик дополнительно ограничивает доступ к конкретному запуску. Неизвестная роль не получает доступ. Отдельная роль наблюдателя ещё не вводилась.
- GET не изменяет материалы, версии, аудит и не вызывает внешние службы. Изменяющие новые маршруты на этом этапе отсутствуют.

`candidateCounts.linked` считает только явно связанные анкеты. `unassignedForRole` доступен только владельцу/HR и не считается числом кандидатов конкретного запуска. `quarantine=null` означает, что карантин пока не реализован, а не ноль кандидатов. Общий `migration` содержит количество неподвязанных публикаций и анкет; руководителю он не раскрывается.

## Границы и риски

- Production не изменён. Доступа к рабочей базе в этом этапе не было. Проверка на обезличенной копии рабочей базы и нагрузочная проверка ещё требуются перед выкладкой.
- Старый интерфейс и старые обработчики кандидатов не переключены на новый вычислитель. `canProcessCandidates=false` и `candidateIntakeMode=quarantine` пока только описывают требуемый режим. Они не являются реализованным запретом отправки, оценки или продвижения. API явно возвращает предупреждение и `candidateProcessingGateImplemented=false`.
- Адаптер работает синхронно после старых операций записи и при запуске сервера. Чтение не запускает миграцию. На большой базе нужно замерить стоимость обновления всех старых запусков и при необходимости сузить обновление до изменённого запуска.
- Старые записи без достаточных связей не потеряны, но не объявлены полностью перенесёнными. Новая привязка кандидатов, полноценный импорт, карантин, утверждения и команды запуска остаются последующими этапами.
- Нельзя выкладывать этот этап отдельно как завершённую защиту воронки. Не выполнены все 14 критериев полного ТЗ; проверено только серверное основание этапа 1.

## Следующее действие

Руководитель проекта проверяет изменения относительно foundation PR #1 и принимает или возвращает этап 1 по Issue #2. После приёмки отдельно передаёт этап 2: управление версиями и человеческими утверждениями. Рабочая выкладка по-прежнему требует отдельного разрешения Андрея.
