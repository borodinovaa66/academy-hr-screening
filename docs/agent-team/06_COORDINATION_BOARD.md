# Координационная доска проекта Academy HR Screening

Обновлено: 2026-09-15

Владелец доски: руководитель проекта.

Назначение: единый реестр задач и артефактов, которые одна роль передаёт другой. Доска не заменяет профильные документы и GitHub Issues: она связывает источник, исполнителя, результат, зависимости и статус в одну проверяемую цепочку.

## 1. Как пользоваться доской

1. Автор создаёт карточку, когда его результат требует действия другой роли.
2. Пока исходный материал не готов, карточка имеет статус `ЧЕРНОВИК`.
3. Автор переводит карточку в `ГОТОВО К ПЕРЕДАЧЕ`, только когда существует исходный артефакт и заполнены критерии приёмки.
4. Получатель проверяет комплектность и переводит карточку в `В РАБОТЕ`.
5. Если без решения нельзя продолжать, получатель ставит `НУЖНО РЕШЕНИЕ`, указывает ровно один вопрос и владельца решения.
6. После выполнения получатель ставит `НА ПРОВЕРКЕ`, прикладывает результат и доказательства проверки.
7. Автор постановки или руководитель проекта ставит `ЗАВЕРШЕНО`, когда критерии приёмки подтверждены.

Задача на изменение кода должна иметь ссылку на GitHub Issue. Методический, продуктовый, дизайнерский или исследовательский артефакт может передаваться ссылкой на файл в репозитории. Если из него возникает разработка, создаётся связанный Issue.

## 2. Допустимые статусы

| Статус | Что означает | Кто ставит |
| --- | --- | --- |
| `ЧЕРНОВИК` | Передача ещё не укомплектована | Автор |
| `ГОТОВО К ПЕРЕДАЧЕ` | Источник и критерии готовы | Автор |
| `В РАБОТЕ` | Получатель принял ответственность | Получатель |
| `НУЖНО РЕШЕНИЕ` | Есть конкретный блокирующий вопрос | Получатель или руководитель проекта |
| `НА ПРОВЕРКЕ` | Результат готов к приёмке | Получатель |
| `ЗАВЕРШЕНО` | Приёмка подтверждена | Автор или руководитель проекта |
| `ОТМЕНЕНО` | Работа остановлена, причина записана | Руководитель проекта |

## 3. Приоритеты

| Приоритет | Правило |
| --- | --- |
| `P0` | Production остановлен, утечка данных или критическая кадровая/юридическая ошибка |
| `P1` | Блокирует текущий релиз, пилот или работу другой роли |
| `P2` | Плановая работа с подтверждённой ценностью |
| `P3` | Идея или улучшение без обязательства взять в ближайший цикл |

Руководитель проекта разрешает конфликт приоритетов. Агент не повышает приоритет своей карточки без объяснения влияния на пользователя, деньги, срок или зависимую работу.

## 5. Шаблон карточки

Скопируй блок целиком и замени подсказки. Идентификатор: `HR-XFER-YYYYMMDD-NN`, где `NN` — следующий свободный номер за день.

```md
### HR-XFER-YYYYMMDD-NN — Короткое название результата

- Статус: `ЧЕРНОВИК`
- Приоритет: `P2`
- Создано: `YYYY-MM-DD`
- Обновлено: `YYYY-MM-DD HH:MM +04:00`
- Автор: `[роль] / [название задачи или ветки]`
- Получатель: `[роль] / [название задачи или ветки, если известно]`
- Владелец следующего действия: `[одна роль или Андрей]`
- Зачем это нужно: `[какой пользовательский или бизнес-результат зависит от передачи]`
- Исходный артефакт: `[кликабельная ссылка на файл, коммит, PR или документ]`
- Связанный GitHub Issue: `[ссылка или "не нужен — код не меняется"]`
- Зависимости: `[ID карточек или "нет"]`
- Что нужно сделать: `[один конкретный проверяемый результат]`
- Критерии приёмки:
  - `[критерий 1]`
  - `[критерий 2]`
- Не входит в задачу: `[явная граница]`
- Риски и ограничения: `[что может исказить или заблокировать результат]`
- Результат и проверка: `[заполняет получатель перед статусом НА ПРОВЕРКЕ]`
- Следующее действие: `[глагол + владелец + ожидаемый результат]`
```

## 6. Пример: методолог передаёт анкету разработчику

```md
### HR-XFER-20260101-01 — Анкета первичного отбора для вакансии менеджера проекта

- Статус: `ГОТОВО К ПЕРЕДАЧЕ`
- Приоритет: `P1`
- Создано: `2026-09-15`
- Обновлено: `2026-09-15 18:00 +04:00`
- Автор: `методолог / role-package-project-manager`
- Получатель: `разработчик платформы / будет назначена при приёме`
- Владелец следующего действия: `разработчик платформы`
- Зачем это нужно: `добавить в платформу проверяемый сценарий отбора для новой вакансии без ручного переноса вопросов`
- Исходный артефакт: [`04_PLATFORM_QUESTIONNAIRE.md`](../role-packages/project-manager/04_PLATFORM_QUESTIONNAIRE.md)
- Связанный GitHub Issue: `создать до перевода в В РАБОТЕ`
- Зависимости: `нет`
- Что нужно сделать: `добавить анкету как конфигурацию вакансии менеджера проекта и отобразить её в кандидатском сценарии и админке`
- Критерии приёмки:
  - `все обязательные вопросы из исходного артефакта присутствуют без смысловых изменений`;
  - `скоринг и стоп-факторы соответствуют утверждённой методике`;
  - `кандидатский сценарий и админка проходят локальную проверку`.
- Не входит в задачу: `публикация вакансии на hh.ru и production-деплой`
- Риски и ограничения: `методолог подтверждает смысл вопросов; разработчик не меняет методику самостоятельно`
- Результат и проверка: `заполняется разработчиком`
- Следующее действие: `разработчик создаёт GitHub Issue, связывает его с этой карточкой и переводит карточку в В РАБОТЕ`
```

Пример показывает формат, но не является активной задачей и не разрешает разработку или деплой.

## 7. Контроль зависших задач

Руководитель проекта при каждом координационном обзоре проверяет:

- карточки `ГОТОВО К ПЕРЕДАЧЕ` без получателя;
- карточки `В РАБОТЕ` без обновления и следующего действия;
- карточки `НУЖНО РЕШЕНИЕ` без самодостаточного вопроса владельцу;
- результаты `НА ПРОВЕРКЕ` без доказательств проверки;
- дублирующие карточки и конфликтующие изменения одних файлов;
- GitHub Issues без обратной ссылки на карточку;
- карточки без существующего исходного артефакта.
